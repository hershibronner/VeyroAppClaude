## Lifecycle hand-offs
1. **Lead → Client (CRM)**: convert keeps the same `companies.id` (stage→'client', lead_status→'converted'), optionally creates an Opportunity and/or a Position (CRM inserts the `positions` row directly: status 'draft', title, company_id, openings, created_by). Opportunity **Won** → company stage 'client' + optional Position (same direct insert). Emits `lead.converted`.
2. **Position recruiters (RECRUITING)**: `position_recruiter_assignments`; the position link is a `sourcing_links` row (user_id, position_id, token). Public URL: `/apply/<org slug>/p/<token>` for position links and `/apply/<slug>/r/<token>` for personal links (both resolve attribution server-side by token).
3. **Offer accepted (RECRUITING)** → candidate signs in the Candidate Portal; then staff click "Create placement" which navigates to `/workforce/placements/new?offerId=<id>`.
4. **Placement create (WORKFORCE)**: `POST /api/v1/placements` body `{ offer_id?, candidate_id?, worker_id?, company_id, position_id?, title, start_date, schedule_days, schedule_start, schedule_end, timezone, weekly_hours, account_manager_id, recruiter_id, sales_id, monitoring_policy_id, pay_rate_cents, bill_rate_cents, currency, unit }`. It reuses or creates the `workers` row for the candidate (same person, `workers.candidate_id`), sets candidate status 'hired', submission 'hired', offer.placement_id, inserts the initial `placement_rates` row (effective_from = start_date), and builds `placement_onboarding_items` = agency default template + client template (onboarding_templates.company_id) + position_requirements + manual. Status 'onboarding'.
5. **Activation (WORKFORCE)**: blocked by incomplete **required** items (409 listing titles); override needs reason (audited, notifies owners/admins). On activate: placement 'active', worker 'active', `seat_usage` row started (audited 'seat.started'), emit `placement.started`. Does NOT email the worker. "Invite to Worker Portal" is a separate action: creates `invitations` (role 'worker', worker_id) and sends template `invite_worker_portal` with link `${WEB_URL}/invite/<token>`. Ending a placement ends the seat (`seat_usage.ended_at`, audited 'seat.ended') and emits `placement.ended` / `worker.terminated`.
6. **Rates (FINANCE)**: `GET /api/v1/placements/:id/rates` (timeline, comp-gated) and `POST /api/v1/placements/:id/rates` `{ effective_from, pay_rate_cents, bill_rate_cents, currency?, unit?, ot_multiplier_bp?, ot_threshold_minutes?, reason }` → uses `planRateInsert`, closes prior row, inserts new row, audit `rate.created`, notifies finance + AM. WORKFORCE's placement detail "Rates" tab calls these endpoints.
7. **Timesheets (WORKFORCE+TIME)**: weekly per placement (Mon start), built from `time_entries` (minutes = ended-started − break − discarded idle). Approve: agency and/or client per `companies.timesheet_approval` ('agency'|'client'|'both'); on final approval write `timesheet_days` snapshot, status 'approved', emit `timesheet.approved`, notify worker + AM, audit. Reject requires reason → 'rejected' (worker can resubmit). Post-approval changes = `timesheet_adjustments` rows (never edit approved days). FINANCE reads `timesheet_days` where `invoice_id IS NULL` (invoicing) / `payroll_item_id IS NULL` (payroll) and sets those columns; when all days of a timesheet are invoiced and paid, FINANCE sets timesheet status 'locked'.
8. **Simulated week (WORKFORCE+TIME)**: the worker tracker's "Demo: simulate a workday" and staff "Simulate rest of week" create realistic entries, screenshots, activity, and can submit the timesheet.
9. **Invoices (FINANCE)**: generated from approved `timesheet_days` per client + period; one line per placement per rate period (`linesByRate`). Send → template `invoice_sent` with pay link `${WEB_URL}/pay/<pay_token>`; payment via simulated Stripe updates status/AR; emits `invoice.sent` / `invoice.paid`; overdue set by a daily job (emit `invoice.overdue`).
10. **Payroll (FINANCE)**: runs per period with idempotency key `payroll:<start>:<end>`; payouts batch to simulated Wise (Initiated→Processing→Paid/Failed over ~10–30s via jobs), retry failed items; payslips (PDF) visible in Worker Portal `pay`.
11. **Attendance (WORKFORCE+TIME)**: a recurring check marks workers late/absent vs placement schedule (in placement timezone), inserts `attendance_events`, and emits `attendance.late` `{ worker_id, worker_name, placement_id, company_id, company_name, account_manager_id, minutes }` / `attendance.absent`.
12. **Automations (INSIGHTS+OPS)**: engine = `onEvent` listener for event-triggered automations + `every()` scheduler for schedule-triggered ones (the 5 seeded automations in `automations` must actually run). Recipient keywords: `account_manager` → payload.account_manager_id (or placement's AM), `attributed_recruiter`, `worker`, `client_contact`, `role:<key>`.
13. **Webhooks (ADMIN+PLATFORM)**: `onEvent` listener delivering to `webhook_endpoints` with HMAC-SHA256 hex of the JSON body in header `x-veyro-signature`, plus `x-veyro-event`, `x-veyro-delivery`; retries with backoff; delivery log & replay. Local receiver already exists at `POST /api/v1/dev/webhook-receiver/:slug`.
14. **Search (INSIGHTS+OPS)**: `GET /api/v1/search?q=` → `{ results: [{ type: 'client'|'lead'|'contact'|'candidate'|'worker'|'position'|'invoice'|'document'|'message', id, title, subtitle, link }] }`, permission-filtered (skip types the role cannot view; respect comp/portal restrictions).
15. **Seats & billing (ADMIN+PLATFORM)** reads `seat_usage`; $29/seat/month (+tax), trial/standard/white_label, comped flag.
16. **AI (RECRUITING)**: deterministic local adapter in `apps/api/src/adapters/ai.ts`; honours `getSetting(orgId,'ai').simulate_failure` (throw a friendly 503 "AI provider unavailable — try again or fill fields manually") and integration status. ADMIN's Settings → AI page toggles that setting via `/api/v1/settings/ai`.
17. **Integrations status**: adapters check `integrations` row status for their key ('payments','payouts','accounting','email','ai',...) and append to `integration_logs`; ADMIN builds the Integrations page (connect/disconnect/reconnect, logs).
18. **Notifications preferences** table is used by `notify()` automatically. INSIGHTS builds `/comms/notifications` (list + preferences); ADMIN builds `/settings/notifications` (admin event subscriptions = `notification_preferences.subscribed`).
19. **Client portal home** (`/portal/client`, WORKFORCE+TIME) shows team status now, hours this week, and invoices due (call FINANCE's `GET /api/v1/portal/client/invoices?status=open` — FINANCE must support that filter).
